### Confirmed implementation risks

- **Existing identifiers can be rewritten.** Custom assignment compares the newly built SKU with the current one and writes when different; it has no empty-only guard. SkyVerge's enabled slug modes can also rewrite existing parent and variation identifiers.
- **Custom format is not an unconditional variation-ID suffix schema.** `sc_build_sku_from_product()` produces `CUSTOMER-PRODUCT-BRAND-STYLE-COLOR-SIZE-{AUTO ATTRIBUTES}`, normalizes and truncates at 180 characters. Missing values become `NA`; customer can fall back to the first product category. `sc_make_unique_sku()` initially retains the base; on collision it tries `-2` through `-999`, then product ID. The stable ID is only the fallback, not appended to every variation.
- **Direct-meta consistency gap.** Custom builder writes `_sku` with `update_post_meta()` and deletes product transients. Reviewed assignment does not use Woo `set_sku()/save()` or explicitly refresh product lookup tables. WP Wham also writes post meta directly when enabled. Lookup/cache/uniqueness drift is a risk to test, not a diagnosed database inconsistency.
- **Batch endpoint hardening is needed before choosing this as authority.** Installed custom handler intentionally omits nonce validation, checks `manage_woocommerce`, reads GET parameters and can automatically continue batches. A state-changing GET without request-intent protection presents a CSRF/accidental-navigation risk. It was neither invoked nor exploit-tested. Recommend a separately reviewed POST/nonce-protected, resumable job design; preserve capability checks and add bounded progress/idempotency.
- **SkyVerge callback spelling mismatch.** Registered non-AJAX `maybe_save_varation_sku` does not match implemented protected `maybe_save_variation_sku`. This is an actual source inconsistency; whether the affected path executes here remains untested. Do not manufacture a product-save failure to prove it.
- **Application format differs too.** Mockup Studio uses a normalized Color/Size/Logo digest, not a universal Woo variation-ID suffix. A broad custom rebuild could replace it. The handoff's suggested Brand/Style/Color/Size + stable variation identity needs an explicit owner decision and migration design, not a claim that one current plugin already implements it exactly.

## Why diagnostics showed only two candidates

`wpPluginSlug()` returns the folder before `/`. The detector allowlist contains `wc-sku-builder-manager`, while the actual folder is **`wc-sku-builder-manager-v3-clean`**. It therefore omits the active custom builder. The plugin-list `data-slug` and actual basename are different identifiers. The storefront has the analogous `...client-stores` versus `...client-storefronts` mismatch.

A local call to the existing pure `summarizePlugins()` with the four actual basenames returned `storefront:null` and exactly two SKU candidates, reproducing the visible diagnostic result without network writes. Recommend exact basename aliases with regression tests. Also show internal enable-state evidence separately where available: WP Wham being listed is not proof it currently generates SKUs. **No application code fix is included in this reports-only PR.**

## Downstream ownership and historical-order risk

Woo product identity, current SKU and historical order/pull-sheet identity are separate. Application webhook source prefers remembered variation-ID mappings, then remembered SKU mappings and other variation/SKU/product fallbacks. Those fallbacks reduce dependence on a single parseable SKU but do not prove every existing order has a valid immutable mapping.

The reviewed custom builder explicitly disables the Supabase sync call during assignment. Its completion screen recommends subsequent sync/catalog steps, but those are not automatically performed and are not authorized by this audit. A SKU rebuild does **not** by itself synchronize products, repair `blank_product_id`, reconcile reservations or update all remembered mappings. Review existing order lines, IDs, reserved demand and provenance before any approved migration; do not rewrite placed-order history to match a new naming scheme.

## Recommended authority decision and staged acceptance

**Do not designate a single winner from activation alone.** Evidence supports two currently enabled admin writers and an explicit application publishing scheme. The custom builder most closely resembles the requested human-readable Brand/Style/Color/Size schema, but its rewrite behavior, collision suffix, direct-meta handling and batch endpoint need remediation before it can be recommended as sole authority. SkyVerge is demonstrably configured to use slug schemes. WP Wham is currently disabled internally and should remain outside any ownership assumption.

Owner decisions needed: immutable identity policy; whether SKUs change after creation; whether Mockup Studio's deterministic variation scheme is retained; treatment of legacy product names/attributes; and the authorized migration window. Suggested target: one explicitly documented creation rule per integration boundary, preservation of nonempty approved identifiers, Woo-safe uniqueness/cache handling, and an intentional separately approved repair operation. If the business demands one uniform format, migrate to it only with full mapping/history acceptance.

After isolated staging is approved, use fictional parent/products with four colors, adult/youth overlapping sizes, at least two logos, a duplicate normalized name and long values that exercise truncation. For each of the four required paths—new creation, individual edit, variation save and bulk/rebuild—record before/after IDs, SKUs, attributes, hook route, metadata/lookup agreement and collisions. Include AJAX and REST separately. Verify second-run stability, untouched products, order-line provenance and failed-batch recovery. Use a separate fake Supabase/project or local stub; validate Woo sync, blank linking, a fictional pull sheet and reservations only after independent approval. No real integrations may receive test events.

Estimated effort after an isolated fixture exists: 4–8 engineering hours to instrument/reproduce all save paths, plus remediation and retest time based on findings. No production deactivation or SKU change is recommended for immediate execution from this document.
